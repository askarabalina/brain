# Телеграм

Бот над той же базой знаний. Нужен, чтобы спрашивать с телефона и диктовать
заметки голосом, когда ноутбук закрыт.

Работает на [nanobot](https://github.com/HKUDS/nanobot) — он даёт канал
телеграма, расшифровку голосовых, белый список и расписание из коробки.
Своего кода тут нет, только конфиг.

## Что доступно с телефона

| | Телеграм | Компьютер |
|---|---|---|
| Задачи Hub: читать | да | да |
| Задачи Hub: комментарий | да | да |
| Задачи Hub: создать задачу | да | да |
| Задачи Hub: статусы, сроки, удаление | **нет** | да |
| База знаний: читать | да | да |
| База знаний: заметка | да | да |
| Справочник личных данных | **нет** | да |

Границы задаются списком `enabledTools`: незарегистрированный инструмент
модель вызвать не может, как бы её ни просили.

```
MCP: registered tool 'mcp_brain_whoami'
MCP: skipping tool 'mcp_brain_get_reference' (not in enabledTools)
```

## Три слоя защиты записи

Запись в Execution Hub с телефона включена. Честно про то, насколько она
защищена — слои разной прочности.

**1. Короткий список инструментов — настоящая граница.** Доступны комментарий
и создание задачи. Смена статусов, сроков и удаление не зарегистрированы
вовсе: их последствия видит вся команда, а откатить сложнее. Это запрет
на уровне рантайма, обойти его нельзя.

**2. Подтверждение кнопкой — соглашение, а не стена.** Правила в
`SOUL.example.md` требуют показать черновик и дождаться «Опубликовать».
В nanobot это не гарантируется механически: его хуки только наблюдают
за вызовами инструментов и не могут их отменить. На практике работает,
но закладываться как на блокировку нельзя.

**3. Журнал — то, что ловит ошибки первого и второго слоя.** После каждой
записи бот вызывает `log_action`, и отправленный текст попадает в
`audit/ГГГГ-ММ.md` с датой и целью. Файл коммитится в git. Это единственный
способ увидеть всё, что ушло наружу с твоего имени, не перебирая задачи
в Hub руками.

**Проверяй журнал раз в неделю.** Если в нём окажется запись, которой ты
не подтверждала, — второй слой не сработал, и список инструментов надо
урезать обратно.

### Самое сильное, что можно сделать

Попроси у администратора Execution Hub **токен с минимальными правами**:
чтение плюс комментарии, без смены статусов и удаления. Тогда граница
окажется на стороне Hub, а не в конфиге бота, и никакая ошибка модели
её не перейдёт.

Это ровно то, что требует раздел ИБ в ТЗ: «токены выдаются по принципу
минимальных прав».

## Что нужно

**1. Бот.** [@BotFather](https://t.me/BotFather) → `/newbot` → токен.

**2. Свой Telegram ID.** [@userinfobot](https://t.me/userinfobot) пришлёт число.
Без белого списка бот ответит кому угодно.

**3. Ключ модели.** Тут важное: **подписка Claude Max не даёт доступа к API.**
Это разные вещи, и nanobot умеет только API-ключ.

Варианты:

| Вариант | Что нужно |
|---|---|
| Anthropic API | ключ в [console.anthropic.com](https://console.anthropic.com), оплата по токенам, отдельно от подписки |
| Google Gemini | ключ в Google AI Studio, есть бесплатный уровень |
| Уже имеющийся OAuth | `nanobot provider login github-copilot` или `xai-grok`, если такие подписки есть |

Расход на бота небольшой: утренняя сводка и несколько вопросов в день — это
единицы долларов в месяц. Поставь месячный лимит в консоли провайдера.

**4. Доступ к Execution Hub.** Тот, что работает в Claude Code, идёт через
коннектор claude.ai — nanobot им пользоваться не может. Нужен прямой адрес
MCP-сервера и токен, их выдаёт администратор Execution Hub.

Если его пока нет, бот всё равно полезен: база знаний, проекты, продукты
и заметки работают без Hub. Задачи добавятся, когда появится доступ.

**5. Распознавание речи** — для голосовых. Ключ любого сервиса, который
поддерживает nanobot.

## Установка

```bash
# nanobot, если ещё не стоит
git clone https://github.com/askarabalina/project.git nanobot
cd nanobot && python3 -m venv .venv && source .venv/bin/activate && pip install -e .

# конфиг
mkdir -p ~/.nanobot
cp ПУТЬ/К/brain/telegram/config.example.json ~/.nanobot/config.json
```

В конфиге замени `ПУТЬ/К/brain` на настоящий путь — в двух местах, `command`
и `BRAIN_DIR`.

Секреты в конфиг **не вписывай**: они подставляются из переменных окружения
через `${ИМЯ}`. На ноутбуке положи их в `~/.nanobot/env` и подгружай перед
запуском. На сервере они лежат иначе — в `/etc/nanobot.env` от root, чтобы
бот не мог прочитать собственные ключи; см. [`deploy.md`](./deploy.md).

```bash
export ANTHROPIC_API_KEY=...
export TELEGRAM_BOT_TOKEN=...
export TELEGRAM_USER_ID=...
export EXECUTION_HUB_MCP_URL=...
export EXECUTION_HUB_TOKEN=...
export TRANSCRIPTION_API_KEY=...
```

```bash
chmod 600 ~/.nanobot/env
```

Запуск:

```bash
source ~/.nanobot/env
nanobot gateway
```

Правила поведения — в рабочую папку бота:

```bash
mkdir -p ~/.nanobot/workspace
cp ПУТЬ/К/brain/telegram/SOUL.example.md ~/.nanobot/workspace/SOUL.md
```

Без этого файла бот будет писать в Hub без черновика и без журнала.

Проверка — напиши боту:

> что ты про меня знаешь

Должен ответить из `profile.md`. Потом:

> что у меня горит

## Чтобы приходил только ответ

По умолчанию бот показывает каждый свой шаг отдельным сообщением: `$ команда`,
обращение к базе, вызов Hub. На компьютере это полезно, в телефоне — лента
из тридцати пузырей, в которой ответ надо искать.

В секции `channels.telegram`:

```json
"send_tool_hints": false,
"show_reasoning": false
```

Первое убирает шаги, второе — рассуждения модели. Остаётся индикатор
«печатает» и готовый ответ. После правки `systemctl restart nanobot`.

Третий флаг, `send_progress`, оставлен включённым: он отвечает за текст,
который бот дописывает по ходу длинного ответа, а не за служебные вызовы.

**Чем это оплачено.** Пузыри с шагами — единственное место, где видно, что
бот делает на сервере. У него есть доступ к оболочке (`tools.exec`, включён
по умолчанию): он может ставить пакеты, читать файлы, запускать команды.
Выключив показ, ты перестаёшь это видеть в момент выполнения.

Что остаётся вместо:

```bash
journalctl -u nanobot -f        # все вызовы, с сервера
```

и журнал `audit/` — но он ловит только запись в Hub, не команды оболочки.

Оболочка не нужна — выключи её совсем, тогда и смотреть будет не на что:

```json
"tools": { "exec": { "enable": false } }
```

Выключено в примере конфига. Проверено, к чему приводит включённая: на просьбу
«дай протокол встречи» с приложенным файлом бот пошёл ставить `faster_whisper`
в `/tmp` и считать расшифровку на двух ядрах. Со стороны это выглядит как
зависший бот.

## Расшифровка записей

Отправленный файл расшифровывается — но не ботом и не на сервере.

Сервер только принимает и держит: телеграм-канал nanobot сам кладёт всё
присланное в `~/.nanobot/media/telegram/`, без участия модели. Считать там
нечем — два ядра без ускорителя, час записи превращается в час ожидания.

Работает ноутбук. `scripts/zabrat_zapisi.py` раз в десять минут забирает новые
записи, расшифровывает локально через `whispermlx` с разделением по говорящим
и присылает готовый документ обратно в телеграм. Настройка — в самом скрипте
и в `scripts/zapisi.example.env`.

Запись при этом никуда не уезжает: сервер в Казахстане, расшифровка
на ноутбуке, облачные распознавалки не участвуют. Это и есть причина такой
схемы — иначе проще было бы отдать файл в любой сервис за сто тенге.

**Два ограничения, про которые надо помнить:**

Ответ приходит, когда ноутбук включён. Отправила ночью — документ будет утром.

Телеграм не отдаёт боту файлы больше 20 МБ. Голосовое сообщение на час влезает,
запись из диктофона телефона обычно нет — такую сначала через
`scripts/podgotovit_audio.py`.

Короткие файлы, меньше трёх минут, скрипт пропускает намеренно: иначе
документ прилетал бы на каждую надиктовку.

**Голосом бот поручения не принимает.** Звук он не слышит — облачного
распознавания нет, и это решение, а не поломка. Надиктованное голосовым
до него не доходит; текст, который телеграм показывает под волной, боту
не передаётся. Поручения пишутся текстом.

Отличить одно от другого он может: телеграм помечает голосовое как `voice`,
а присланный файл как `audio` или `file`. На первое он просит повторить
текстом, на второе отвечает, что запись принята.

**Не всякую запись стоит нести через бота.** Телеграм в этой цепочке участвует
дважды — принимает звук и отдаёт текст, — и оба остаются в переписке. Для
внутреннего планирования и разговоров с оценками людей есть второй путь:
папка `~/Записи/расшифровать/` на ноутбуке, мимо телеграма и мимо сервера.
Описан в навыке `transkribirovat`.

**Онлайн-встречи сюда вообще не носи.** Teams и Zoom расшифровывают сами,
и подписывают говорящих настоящими именами вместо «Говорящий 2». Подробности
в навыке `transkribirovat`.

## Утренняя сводка

Когда бот заработает, попроси его прямо в телеграме:

> каждый будний день в 8:30 присылай сводку: сначала блокеры с числом дней
> молчания, потом просрочки, потом сроки на сегодня

Он заведёт себе расписание через инструмент `cron`.

**Но:** сводка придёт, только если бот в этот момент запущен. На ноутбуке это
значит «если он включён и не спит» — то есть в 8:30 скорее всего нет.

Для настоящей утренней сводки нужна машина, которая не выключается.
Развёртывание на сервере — [`deploy.md`](./deploy.md): туда же вынесены
требования к железу и служба systemd, чтобы бот переживал перезагрузку.

Сервер под бота нужен простой: публичный IP, домен, TLS и согласование
с ИБ не требуются, потому что входящих подключений он не принимает.

До сервера бот работает как «спросить с телефона, пока ноутбук включён» —
это тоже полезно, просто не автоматически.

## Безопасность

- Переписка с ботом уходит на серверы телеграма. Для рабочих вопросов
  по проектам это обычно приемлемо, для данных под NDA — нет. Раздел
  «Границы» в `profile.md` действует и здесь.
- Белый список обязателен: без `allow_from` бот отвечает любому, кто найдёт
  его по имени.
- Токен бота — секрет. Утёк — отзови через BotFather и выпусти новый.
- Запись в Execution Hub и справочник личных данных закрыты списком
  `enabledTools`. Не убирай их оттуда «на время», чтобы что-то быстро
  поправить с телефона: правка в Hub без просмотра черновика — ровно то,
  от чего эта настройка защищает.
